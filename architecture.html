How I Design Salesforce Systems

This page is a reasoning framework, not a client engagement report — it shows how I evaluate trade-offs across automation, security, data, integration, and operations. Specific implementations are covered in the case studies. This content is English-only by design; it's reference material for a technical audience rather than narrative content.

Architecture Principles

These are the defaults I design against — not universal Salesforce law, just the judgment calls I make until a specific constraint says otherwise.

Security by Default

Least privilege, explicit sharing models, and secure execution contexts by default. Access is granted deliberately — it is never inherited by accident because a profile was cloned or a sharing rule was copy-pasted from somewhere else.

Declarative Where It Makes Sense

Flow and configuration own orchestration and process logic by default, because they keep the system transparent and admin-maintainable. This holds until the requirement genuinely needs programmatic control — not because Flow is "easier."

Code With Purpose

Apex earns its place when transaction control, reuse across many entry points, performance under bulk load, or an integration boundary makes the added engineering lifecycle cost — tests, deployments, code review — worth paying.

Integration Through Clear Contracts

Systems communicate through explicit ownership boundaries: which system is the source of truth for a field, what the retry contract is, and what happens when the other side is down. Implicit assumptions are where integrations quietly break.

Observable Operations

A solution isn't finished when the happy path works in a demo. It's finished when whoever supports it in six months can tell what failed, why, and whether it's safe to retry.

Design for Change

Custom Metadata over hardcoded values, modular Flow and Apex over monolithic logic, and clear layer boundaries — because the second change to a system is always cheaper than the first if the architecture allows for it.

Bulkification by Design

I evaluate automations for bulk behavior rather than validating only the single-record happy path. Governor limits don't negotiate, and "it works for one record" is not a passing test.

Trade-offs Are Explicit

No technology choice is free. Choosing Flow over Apex, sync over async, or a custom object over a standard one always trades something for something else — and that trade should be named, not hidden behind a confident tone.

Layered Architecture

My Default Model, Not The Salesforce Model

I organize Salesforce solutions into five layers. This is a starting model I adapt per engagement, not a claim that it's the only correct way to build on the platform.

01 · Experience Layer — LWC · Aura · FlexiPage

Owns role-based interaction surfaces. Components stay data-agnostic by default: they consume services and render state, they don't own business logic. Trade-off: pushing logic down to the service layer means an extra Apex round-trip for things a component could technically compute itself — accepted because it keeps UI logic testable independently of business rules.

02 · Orchestration Layer — Flow · Platform Events

Flow owns orchestration and human-readable process logic by default. Apex is introduced at this layer only as invocable methods called by Flow, for operations exceeding declarative limits. Trade-off: Flow-first orchestration is more maintainable by admins but has a lower performance ceiling and weaker native error handling than an equivalent Apex trigger — acceptable when admin ownership matters more than raw throughput.

03 · Service Layer — Apex · Queueable · Batch

Encapsulates transaction-level logic: reusable Apex services, invocable methods, async processing. Services are designed to be stateless and bulk-safe by default, not as an afterthought. Trade-off: a dedicated service layer adds indirection — a one-off automation could be written faster as an inline trigger — accepted because reuse and testability compound in value as the org grows.

04 · Data & Governance Layer — Objects · Sharing · Validation

Owns schema, validation, and the security model — OWD, role hierarchy, sharing rules, permission sets. This layer is the source of truth: access is earned by the sharing model, never assumed by a UI hiding a button. Trade-off: a strict OWD-private-plus-sharing-rules model is more auditable than a permissive OWD, but requires more upfront design of exactly who needs to see what.

05 · Integration Layer — REST · Named Credentials

Provides secure authentication abstraction and reusable connectivity to external systems, so one integration framework supports many external systems rather than one bespoke class per API. Trade-off: a generic HttpCallout service is more work to build upfront than a hardcoded one-off callout — it pays for itself on the second integration, not the first.

Automation Decision Framework

Flow, Apex, or Hybrid?

Selection depends on context. Here's what I actually weigh, organized by which option it tends to favor.

Admin Maintainability

Business rules change often and the team needs to adjust them without a deployment.

Business Transparency

Stakeholders benefit from being able to read the logic, not just trust that it works.

Complexity

The logic is orchestration-shaped: sequence, branching, and record updates — not heavy computation.

Testability

Flow Tests can cover the paths that matter without needing a full Apex test harness.

Transaction Control

The operation needs explicit savepoints, partial rollback, or precise control over commit boundaries.

CPU / SOQL / DML Behavior

The logic is computation-heavy or needs tight control over query and DML efficiency at bulk scale.

Reusability

The same logic needs to be callable from multiple triggers, batch jobs, and integrations without duplication.

Asynchronous Requirements

The work needs Queueable chaining, Batch Apex, or scheduled processing beyond what Flow exposes cleanly.

Default Pattern

Flow owns orchestration and entry criteria; Apex is invoked only for the specific step that needs programmatic control.

Ownership Split

Admins own the process shape; engineering owns the invocable service contract underneath it.

Deployment Complexity

Two moving parts to release instead of one — worth it when it keeps both maintainability and performance.

Rate of Change

The orchestration shape changes often; the underlying service logic changes rarely. Splitting them lets each evolve at its own pace.

Security Architecture

How the Layers Actually Connect

Salesforce security isn't one setting — it's several layers that have to agree with each other. This is the order I reason about them in:

Identity & Org Access
MFA, login policies, session settings — who can get into the org at all.
↓
Object Access
Profiles for the baseline, Permission Sets and Permission Set Groups for everything additive and role-specific.
↓
Field Access
Field-Level Security — enforced at the object layer, and separately inside Apex when running in user mode.
↓
Record Access
OWD sets the default, Role Hierarchy extends it upward, Sharing Rules and Teams extend it sideways, Apex Managed Sharing covers what declarative rules can't model.
↓
External User Access
Experience Cloud sharing sets and license-specific visibility rules — external users need a narrower, more deliberate model than internal ones.
↓
Runtime Enforcement
Apex sharing keywords (with sharing / without sharing / inherited sharing) control record-level sharing enforcement only. Object and field access (CRUD/FLS) is a separate concern, enforced deliberately through user-mode database operations or explicit checks — not a side effect of the sharing keyword.

The layer that gets the least attention is usually this one. with sharing / without sharing only decide whether record-level sharing rules apply inside that Apex context — they say nothing about object or field access. A class can run with sharing and still return fields a user shouldn't see, if it never enforces CRUD/FLS itself. I treat these as two separate enforcement decisions, not one switch.

Choosing the Right Access Mechanism

Role Hierarchy

  • Visibility should flow upward through management naturally
  • Org structure is stable and mirrors the sharing need
Structural

Sharing Rules

  • Access criteria are predictable and rule-based (by role, group, or criteria)
  • The rule set is small enough to stay auditable
Rule-Driven

Apex Managed Sharing

  • Access depends on dynamic, computed conditions declarative sharing can't express
  • Worth the maintenance cost of code-owned share records
Dynamic

Manual Sharing covers the exceptional, human-judgment case — a single record shared to a single user for a specific reason, not a repeatable pattern. Experience Cloud sharing depends heavily on license type and data model, so I treat it as its own evaluation rather than an extension of internal sharing rules.

Data Architecture

Ownership Before Schema

Before modeling an object, I want an answer to: which system is the system of record for this data, and who is allowed to create or change it? Most data-quality problems I've seen trace back to that question never being answered explicitly.

→
Reporting

Modeling

Relationships

  • Lookup when the relationship is optional or the child can outlive the parent
  • Master-Detail when the child's security and lifecycle should follow the parent
  • Junction objects for genuine many-to-many, not as a workaround for a missing field
Integration Identity

External IDs & Upsert

  • External ID fields as the join key between Salesforce and the system of record
  • Upsert over separate create/update calls wherever idempotency matters
  • One system named as authoritative per field — never two systems both allowed to overwrite the same value
Scale

Volume & Query Performance

  • Selective, indexed filters on any query expected to run against a large object
  • Awareness of data skew (a single account or owner holding a disproportionate share of records) before it becomes a locking problem
  • Archiving strategy considered up front for objects with an expected multi-year growth curve
Quality

Validation & Duplicates

  • Validation rules enforced at write time, not caught later in a report
  • Duplicate rules and matching criteria set deliberately, not left at the org defaults
  • A clear answer for what "clean" means for each object before automation starts enforcing it

This is the evaluation framework I bring to a data model. Advanced Large Data Volume patterns (skew remediation at scale, deep archiving strategies) are exactly what the Platform Data Architect credential formalizes — I'm building toward that certification rather than claiming production experience at that scale today.

Operational Architecture

Finished Means Supportable, Not Just Working

A solution isn't done when the happy path works in a sandbox. It's done when someone who isn't me can find out what failed and fix it.

Monitoring

What Needs Watching

  • Flow fault paths and Apex exceptions, not just successful runs
  • Asynchronous job health — Queueable, Batch, and Scheduled Apex failures
  • Integration and event processing backlogs
Logging

What a Useful Log Entry Contains

  • A correlation ID that ties a failure back to the record and transaction it came from
  • Execution context, external system involved, and an error classification — not just a raw stack trace
  • Retry state, so it's clear whether a failure is still being worked or already exhausted
Alerting

Severity & Ownership

  • Severity tied to business impact, not just "an error occurred"
  • A clear owner for each alert class — admin, developer, or an external team
  • An escalation path defined before the first incident, not during it
Recovery

Getting Back to Healthy

  • Retry and replay mechanisms designed to be idempotent — safe to run twice
  • Manual remediation paths documented for the failures automation can't self-heal
  • A support handoff that assumes the original builder isn't the one debugging it
Architecture Risks

What I'm Watching For

These are the risk patterns most relevant to Flow/Apex-heavy Salesforce architectures — the ones I check for on every build, not a generic compliance checklist.

Governor Limit Saturation
SOQL, DML, and CPU limits are per-transaction, and they don't scale just because the org grows.
Mitigation: bulkified triggers and Flows by default, async boundaries (Queueable/Batch) for anything that could exceed synchronous limits.
Automation Recursion
A Flow or trigger that updates the same object it's triggered from can re-enter itself, unintentionally.
Mitigation: strict entry criteria, recursion guards, and testing the "what if this fires twice" case explicitly.
Permission Drift
Profiles and permission sets accumulate one-off changes over time until nobody can explain why a user can do something.
Mitigation: Permission Sets and Permission Set Groups over profile cloning, and periodic access review built into the operating model.
Integration Outage
An external system going down shouldn't take the Salesforce transaction down with it.
Mitigation: async decoupling for non-blocking calls, persistent error logging so failures are visible instead of silent.
Data Skew
A disproportionate number of records under one account or owner can cause record-locking contention during bulk updates.
Mitigation: ownership strategy reviewed before it becomes a production incident, not after.
API Limit Exhaustion
Chatty, one-record-at-a-time integrations burn through daily API limits faster than expected as volume grows.
Mitigation: batching, Bulk API for volume, and Platform Events to absorb spikes instead of synchronous point-to-point calls.
