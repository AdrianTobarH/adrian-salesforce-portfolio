Enterprise API
Integration Layer

Reusable Named Credential architecture with secure REST endpoints and a configuration-driven service layer — an integration foundation designed to extend to additional external systems without new code per integration.

Composite case study based on real Salesforce production work. Client-specific details have been anonymized and generalized; some elements combine patterns from multiple engagements.

Context

Business Problem

  • API credentials hardcoded in Apex — critical security vulnerability
  • No reusable integration pattern — each system required bespoke code
  • External data sync running on nightly batch only — no real-time option
  • Zero error handling — failed callouts silent with no retry mechanism
Architecture Strategy

Solution Design

  • Named Credentials as the single source of truth for outbound credentials — no secrets stored in Apex
  • A reusable Apex service class as the single integration point for REST callouts, replacing bespoke per-system code
  • Custom object logging layer for callout auditing and retry visibility
Architecture Alternatives

Why Not Middleware?

  • Hardcoded per-integration credentials — the problem this design replaces, not a real alternative.
  • Middleware / iPaaS layer — a stronger fit at higher integration counts or when external systems need to talk to each other directly; not necessary here since Named Credentials solved the immediate need without new infrastructure or licensing.
  • Named Credentials + reusable service class (used in this design) — centralizes secret management without adding a new platform dependency.
Architecture Considerations

Patterns I'd Evaluate at Scale

  • OAuth 2.0 Auth Provider for automatic token refresh, where the external system supports it, instead of managing tokens manually
  • Platform Events to decouple downstream sync from the request transaction, when near-real-time updates matter more than immediate consistency
  • Apex Queueable chaining for retry-safe asynchronous callout sequences
  • External Services for no-code API schema registration, where the external API exposes a stable OpenAPI spec
Security Model

Credential & Runtime Security

  • All outbound credentials stored in Named Credentials — never hardcoded in Apex
  • Apex callouts authenticate through the Named Credential / External Credential layer, not through CSP or CORS — those govern browser- and Lightning-originated requests, not server-side callouts
  • CSP Trusted Sites evaluated separately for any Lightning component that calls the external system directly from the browser
  • Callout logging designed to avoid persisting sensitive response fields, rather than storing raw response bodies indefinitely
Risks & Mitigations

What Could Break

  • Shared service as a single point of failure — one HttpCallout class serving every integration means a bug there affects all of them; mitigated with per-endpoint configuration via custom metadata and isolated error handling per callout rather than one shared catch-all.
  • Duplicate downstream records from retries — a retry without idempotency protection can create the same record twice; mitigated by pairing retry logic with idempotent request keys wherever the external system supports them.
Scalability

Reusable Architecture

  • A single Apex service class supports additional REST endpoints through configuration, rather than a new class per integration
  • Custom metadata for endpoint registration — adding a new API is a configuration change, not a deployment
Business Impact

Delivered Outcomes

  • API secrets moved out of Apex code and into Named Credentials
  • Reusable integration service reduced duplication when adding additional endpoints
  • Callout logging replaced silent failures with visibility into integration health and failure patterns
